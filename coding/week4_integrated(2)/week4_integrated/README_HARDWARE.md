# Coding Day 4：接线、配置与验收

本次修改整合在 `week4_integrated`；原始 member2–member6 和 codingday3 目录保留作参考。改前源码备份在上级 `.changes/week4_before_oled.zip`。

## 共享 I2C1 接线

| 信号 | STM32 | 你们确认的排针 | 连接 |
|---|---|---|---|
| SCL / D15 同行靠里针 | PB8 | CN10-3 | IMU SCL 和 OLED SCL 并接 |
| SDA / D14 同行靠里针 | PB9 | CN10-5 | IMU SDA 和 OLED SDA 并接 |
| GND | GND | 板上 GND | IMU、OLED 与 NUCLEO 共地 |

默认总线为 I2C1、100 kHz。采用与 STM32 兼容的 3.3 V 信号电平，按模块规格供电。上下排针只要连接同一 PB8/PB9 网络，就共用这条总线；没有另建软件 I2C。

老师截图和本目录的课件没有给出 OLED 控制器/分辨率/地址。当前默认按带内部电荷泵的 **SSD1306、128×64、7 位地址 0x3C** 编译；这是一项待实物确认的配置，不能据此认定屏幕型号。支持 128×32、0x3D 参数覆盖；SH1106 需要不同驱动。

## 构建与主机测试

```powershell
python tools/test_python.py
python tools/test_arm.py
python tools/build.py
```

`test_arm.py` 保留旧入口名，实际运行当前 C 源码的主机 mock 回归，**不等于上板或 ARM 仿真测试**。如自动找不到编译器，用 `--cc` 指定主机 GCC，`build.py --gcc` 指定 ARM GCC。Arm 官方便携 GCC 放在上级 `.tools`，构建器会自动查找。其来源为 [Arm GNU Toolchain](https://developer.arm.com/Tools%20and%20Software/GNU%20Toolchain)。

构建输出为 `build/integration/Week4_Integrated.elf`、`.hex`、`.bin`。默认固件启用 OLED、IMU、LiDAR、蓝牙和诊断，但运动保留标定锁。

屏幕尺寸或地址不同，可执行：

```powershell
python tools/build.py --define W4_OLED_HEIGHT=32 --define W4_OLED_ADDR7=0x3d
```

CubeIDE 也可直接导入本目录工程。把相同宏加到需要使用的 Debug/Release C 编译器预处理宏中，不能只在命令行脚本里改。

## 运动标定

`week4/Src/w4_calibration.c` 的 65 mm 轮径、120 mm 轮距和 330 上升沿/圈为待核实值。实测并验证前进电机方向、右轮编码器方向和 IMU 正转方向后，设置 `W4_CAL_DIAMETER_R_M`、`W4_CAL_TRACK_M`、`W4_CAL_CPR_R`、`W4_CAL_ENC_SIGN_R`、`W4_CAL_IMU_SIGN`。最后才使用 `--define W4_CALIBRATED` 构建运动固件。默认 `HARDWARE_NOT_READY` 表示标定锁生效，不是蓝牙损坏。

只有一个 PA7 右轮无方向编码器。右轮位移由脉冲和右电机指令方向推断；左轮速度、车体中心位移结合陀螺仪推算，不能声称独立测量了左右轮速度。滑行只沿用方向最多 200 ms；不明确的反向/外力移动会拒绝该次测量。轮胎打滑和单编码器估计误差仍需实车评估。

## 开机与命令

先保持小车静止。IMU 自动读取身份、唤醒、配置量程/滤波/采样率，连续 200 次静止采样完成零偏标定。IMU 航向从相对零开始，位姿层仅加一次世界偏置，使初始朝向为正 Y。屏幕逐块初始化，128×64 通常需要数秒；任务从开机起每 50 ms 运行，运行时每次最多刷新一个 16 字节块；有变化时优先更新，无变化时循环重写现有块以持续展示 mutex 的真实共享访问，完整画面不是 20 FPS。

每条命令以换行结尾，可由 PC 界面发送：

```text
GOTO,0,1.4
GOTO,-0.7,0.7
GOTO,0.7,-0.7
STOP
RESET
```

每次试验物理放回 `(0,0)` 并朝向正 Y；停止、IMU 已就绪时发 `RESET`，收到 `RESET_PENDING` 后等待下一个 10 ms 控制周期完成复位，再发送一条 GOTO。运动期间 GOTO/RESET 会被拒绝，STOP 独立锁存，队列满也能请求停车。

课件文字要求 `(0.7,-0.7)`，图示却是 `(0.7,0.7)`。两种目标均已支持。负 Y 默认路径是 `(0,0)→(0,-0.7)→(0.7,-0.7)`，需确认场地有这段通道；图示正 Y 路径经 `(0,0.7)` 向右转。代码无法决定实际迷宫的边界。路径点间距默认 5 cm。

## 实际 mutex 与调度证据

IMU 的身份探测、寄存器写入、采样和 OLED 分块写入（包括静止画面的周期重写）均通过 `w4_i2c_bus.c` 的同一个 `Mtx_I2C1`，使用 `osMutexPrioInherit`。异步 I2C 在完成、总线空闲或确认硬件复位后才归还调用方缓冲区并释放 mutex。IMU 超时会使样本无效，连续错误触发恢复和重新初始化。

PC 程序说明见 `README_PC.md`。默认每 50 ms 发送 IMU/导航数据，每秒发送诊断：

- `B`：IMU/OLED 各自获取锁次数、IMU 最大等待 tick、OLED 最大持锁 tick、完成次数、传输超时、恢复次数；tick=1 ms。两种 acquisition 都持续增加才证明两个设备都在访问。
- `S`：定时器触发、采样完成、采样失败、信号量合并、IMU 校准标志、OLED 状态（0 未配置、1 初始化、2 就绪、3 IO 错误）。以两个时间点的完成数差 / 时间差计算实际采样率。
- `T`：每秒轮换一个任务，带优先级、配置栈字节、唤醒次数、最大实际周期/耗时/抖动（微秒）、截止时间错失、最小空闲栈。事件任务的周期是唤醒间隔，不应与固定周期等同。
- `Q`：毫秒、LiDAR 队列当前深度/容量、命令队列深度/容量、路径队列深度/容量、命令队列满次数、路径回压次数。LiDAR 额外序号/覆盖检查见调试器 `LidarDma_GetStats()`。

IMU 10 ms 定时器→二值信号量；编码器/位姿/PID/电机合并在 10 ms 控制任务；OLED 50 ms；蓝牙周期发布 50 ms，DMA 发送事件驱动。耗时统计包围实际处理段，排除下一次事件等待；包含被高优先级任务抢占的墙钟时间，不是纯 CPU 占用。

## 上板验收清单

1. 同时连接真实 IMU/OLED；确认 OLED 状态2、B 帧两设备计数增长；缺失设备须能看到失败而不是伪造成功。
2. 分别记录 IMU 单独运行和 OLED 内容持续变化时至少 30 s 数据，比较实际采样率、最长间隔、等待/持锁时间和合并触发数。必要时用逻辑分析仪解码 PB8/PB9 的 MPU 地址及 OLED 地址，证明没有交错事务。
3. 展示各任务优先级、配置栈和实测余量、10/50 ms 周期与事件唤醒；展示三个队列的数据结构、容量8/8/64和溢出/回压策略。
4. 完成三条目标试验，每次仅发一条 GOTO。用实际测量记录终点 X/Y 误差和航向误差，同时保留 PC 遥测；不能只把内部里程计当成真实位置。
5. 运动中测试 STOP、传感器失效停车、复位后再次导航。验收前完成 PID 参数和几何标定；现场不调参。

主机 mock 测试和 ARM 编译仅证明软件回归与链接；OLED 型号、接线、电气时序、物理路径和终点精度均需实物验证。
